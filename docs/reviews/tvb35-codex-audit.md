### A. Seat-stage l2Book read and effect on the order loop

[MEDIUM] F1 -- The competition census excludes already_in_position despite that refusal occurring after all structural and risk gates. Executor `src/hip3_executor/rules.py:104` includes no_slot_free, cooldown, and day_cap_reached, but not already_in_position. The latter returns at line 467 immediately before the seat-cap check. Consequently `src/hip3_executor/engine.py:806` skips its book entirely. This matters for comparing a new eligible ticket with the incumbent on the same coin; the claimed executable spreads for exactly the competing tickets are incomplete under that interpretation. An offline call with already_in_position returned an empty shadow without a broker call. The saved round-3 ledger has zero such rows, so no observed round-3 count is changed. Include it or explicitly define and name the future seat-competition population as excluding incumbent-coin alternatives.

[HIGH] F2 -- A journal-only shadow adds an unbounded synchronous venue read in front of the order and all subsequent safety polls. Executor `src/hip3_executor/engine.py:751` calls `_book_shadow` before `_enter` at line 799. The broker's new `book_top` at `src/hip3_executor/broker.py:254` uses the shared Info client, constructed at line 144 without a timeout. The locked and locally installed SDK 0.24.0 defaults timeout to None and passes it to the request. Catching exceptions only helps after a request returns or raises; a stalled read can hold the loop indefinitely. The per-poll count cap is neither a wall-clock bound nor a venue-weight proof. This is a real behavioral dependency despite the shadow never being read as a gate: later stop checks, software exits, and kill-file processing wait behind it. Use a separate bounded read path and a total shadow time budget, or collect asynchronously with explicit timestamp/staleness fields. No actual stalled network request was induced during this audit.

[NOTE] The early-refusal selection, coin cache, and call-count cap otherwise check out in source and existing fake tests. Executor `src/hip3_executor/engine.py:740` creates a fresh cache per scan; lines 809-820 cache both success and failure, reuse a coin once, and stop adding distinct reads at 20. The canonical iterator at `src/hip3_executor/rules.py:74` yields the same coin object for every signal on that coin in one snapshot, so those rows have the same mid. A synthetic duplicate-name input with different mids does reuse the first normalized spread; that is a latent input-contract limitation, not evidence of a wrong spread on the canonical iterator. If multiple snapshots or independent row mids are admitted later, cache raw book prices and normalize per row.

Executor `README.md:624` says the weekly open is the daily open on Sun/Mon and duplicates it until midweek; the run README at `runs/2026-09-06_round3_aborted/README.md:19` repeats it. ### D. Macro-regime labels, causality, coverage, and sentences versus tables

[HIGH] F6 -- Entry-time labels use future hourly closes and extremes. Public `analysis/regime/receipt.py:102` selects the latest hourly bar whose OPEN is <= t, then line 111 returns that bar's final close. The class itself documents open timestamps at line 79. `running_day` similarly includes the full current-hour high/low at lines 140-145. At an hour's opening instant, neither the eventual close nor those extremes are yet known. Caching decisions at the hour open at lines 291-295 does not fix this; it applies the completed hour's outcome from its beginning. A synthetic hour opening at 101 and later closing at 90 returned price 90, a down daily dot, and an outside-day flag at the instant it opened. With the exact pinned reference files, 58 of 84 trade entries use a not-yet-complete hour for at least one of the two macro references. Replacing only the price lookup with completed-hour-only data changes the daily composite on 12 entries: eight in round 2 and four in weekend 1. This is a sensitivity reproduction, not a regenerated certified receipt. Repair both price and running extremes, define bar-close availability, then regenerate every affected table and narrative. The current ENTRY-time claims in `analysis/regime/REGIME_RECEIPT.md:3` and line 7 are not causally supported.

[MEDIUM] F7 -- Missing whipsaw history becomes false, overstating coverage and supporting an unjustified inertness conclusion. Public `analysis/regime/receipt.py:184` applies bool to possibly absent reference outside-day values. The pinned BTC hourly history starts after the entire weekend-1 ledger; independent reconstruction confirms `running_day` is None for all 34 weekend trades. Nevertheless all 34 appear in the false group at `analysis/regime/REGIME_RECEIPT.md:73`. If SPX is false and BTC unavailable, the OR predicate is unknown, not false. The helper also lacks the freshness check used for dots, so a closed reference can retain an old running-day state. Therefore two flags out of 84 cannot establish that the label is inert as claimed in public `docs/HANDOFF.md:82`. Preserve true/false/unknown with availability counts, require the declared freshness policy for each component, and obtain sufficient history before using 84 as the measured denominator.

[MEDIUM] F8 -- The headline availability narrative does not match even the existing pinned labels. Public `docs/HANDOFF.md:77` says only 32 of 84 trades are labelable and 29 of 34 weekend entries occurred with both references closed. Exact reconstruction matches the committed receipt labels with zero discrepancies, but those labels contain 22 weekend entries with both closed, seven with DXY up/US10Y down, and five with both down. Both references have available daily dots for 43 trades: 31 round-2 and 12 weekend-1. If labelable means a directional composite rather than available inputs, the receipt has 25 such trades, not 32 (18 with plus seven against at `analysis/regime/REGIME_RECEIPT.md:27`). Define availability, disagreement, and directional alignment separately; regenerate the prose from those counts after F6 is fixed. Characterization language does not excuse a contradictory denominator.

Public `scripts/tvb35_regime_harvest.mjs:76` returns the last dump after exhausting the identity/settling loop.
